本方案用于三人协作完成企业财务问答 Agent 拓展作业。A 先实现可运行的基础 demo，提交 PR，经其他成员审核后合并；B、C 再从合并后的同一个基线版本出发，并行开展数据工具优化和 Agent 策略优化。A 负责后续集成、统一评测和复现，C 是课程报告的唯一撰写人。PR 不设置固定审核人，由小组安排作者以外的成员审核。

## 1 目标与协作原则

### 1.1 最终成果

共同交付一套可复用的 Agent 系统。输入公司 CIK 和英文问题后，由大模型自主决定查询数据库、检索年报、计算指标或继续核查，并形成有依据的回答。

交付内容包括系统代码、数据准备方法、运行说明、初始提示词和 Skill、train 与 test 预测、真实工具日志、实验配置、模型用量和耗时、独立评测结果，以及由 C 统一撰写的报告和 PDF。

### 1.2 开发顺序

```text
A 完成基础 demo
    ↓
A 提交基础 PR → 其他成员审核 → 修改通过后合并
    ↓
记录共同基线提交号
    ├── B 优化数据组织和检索工具 → 提交 PR → 其他成员审核
    ├── C 优化 Agent 策略和 Skill → 提交 PR → 其他成员审核
    └── A 完善统一评测与复现流程
    ↓
A 集成并完成 train 对比实验 → 其他成员审核集成 PR
    ↓
冻结最终方案 → 自动完成 test → 独立评测
    ↓
C 整理报告和 PDF → 其他成员审核报告 PR
```

B、C 的优化开发以 A 的基础 PR 合并为开始条件。此前可以阅读资料和参与接口讨论。基线合并后，B 使用基础 Agent 验证工具，C 使用基础工具验证策略，两人不需要等待对方的优化成果。

### 1.3 报告责任

**C 独自负责报告的提纲、正文、图表编排、引用、格式、修改和 PDF 导出。A、B 不承担报告章节写作。** 如果课程最终提交一份包含四项必做任务与拓展任务的总报告，由 C 统一整合已有材料。

A、B 向 C 提供代码版本、配置、指标文件、方法要点、运行记录和案例位置，并在审阅时指出事实错误。材料以结构化记录和原始结果为主，无需代写报告段落；报告正文由 C 编辑。

## 3 A 的工作与验收标准

### 3.1 第一阶段完成基础 demo

1. 接入一个支持工具调用的模型服务，将模型名称、服务地址、调用预算和数据路径配置化，提供不含真实密钥的配置示例。
2. 加载固定的任务输入，保持 `question_id`、`company_cik` 和 `question` 三个字段；CIK 按字符串处理。
3. 提供基础工具：表结构和指标发现、只读数据库查询、年报关键词检索、数值计算。检索先达到可用水平，为 B 保留替换入口。
4. 实现真实的模型决策与工具调用循环。模型根据工具结果决定下一步行动或结束；固定的数据加载和索引准备可独立执行。
5. 处理工具报错、无结果、超出调用预算和模型服务失败，并区分失败、空回答和正常结束。
6. 提供单题与批量运行入口。每题重新建立会话并加载同一初始状态，支持指定 train 题目进行开发验证。
7. 按老师协议保存预测 JSON 数组，每条至少包含 `question_id` 和字符串 `answer`；SQL、计算和检索过程另存日志。
8. 日志记录实际工具名称、参数、结果或结果文件、错误、耗时和可获得的模型用量，不要求记录模型隐藏思维链。
9. 提供工具接口说明、依赖配置和从仓库根目录运行的命令，保证 B、C 能独立复现。

### 3.2 基础 demo 验收

由 A 从 train 中选取 3 至 5 道题，覆盖数值查询、年报文字检索和计算，尽量包含一次多工具协作。作者以外的审核成员在基础 PR 中检查以下事项：

- 能通过说明中的命令运行，数据路径可以在另一台电脑配置。
- 至少存在真实数据库查询、真实年报检索和真实计算的执行记录。
- 模型参与工具选择及后续行动决策，日志与实际调用一致。
- 预测文件通过官方评测程序的格式检查。
- 基础版和后续优化版有独立的配置入口，能分别运行。
- 单题状态能够重置，原始数据和老师提供的协议未被修改。
- 作答阶段不读取独立评测材料及评分输出。

demo 验收以流程和接口可用为准，不设置支持率门槛。基础版的完整 train 评测可在基础 PR 合并后，由 A 与 B、C 的优化工作同步完成。

### 3.3 基础 PR 合并后的工作

A 记录基线提交号和配置快照，完成 37 道 train 的基线运行与独立评测，保留原始输出。A 同时完善结果汇总、配置选择、预处理耗时和逐题成本统计，不在此期间随意变更已交付给 B、C 的接口。

收到 B、C 的 PR 后，按小组安排完成作者以外成员的审核，A 核对接口与集成结果，再完成组合配置和集成。公共依赖、根目录运行说明和最终复现入口由 A 统一维护。

## 4 B 的工作与验收标准

### 4.1 开发范围

B 从已合并的基础版本创建分支，重点改善工具返回的数据和证据质量：

1. 理解 `schema.md`、`business_rules.md`、公司目录和年报目录，整理通用指标发现与口径元数据，保留原始数据库不变。
2. 改善指标检索、查询结果的字段说明和来源追踪。注意单位、报告期、重复披露、缺失值与不同指标定义。
3. 清洗 9 份 HTML 年报，保留公司、报告期、章节、表格关系、文件路径和可定位的证据标识。
4. 建立按公司、期间和内容检索的索引；派生文件另存，并提供可重复运行的构建方法。
5. 改进检索排序与证据返回，避免将整份年报直接交给模型。采用的算法和参数在配置中记录。
6. 保持基础工具的外部接口兼容，保留基础实现，提供优化开关，支持数据优化单独启用。

优先完成年报检索与来源追踪；指标映射作为同一方向下的补充。B 的改进应能通过基础 Agent 使用，不依赖 C 的 Skill 或新提示词。

### 4.2 验收与材料

- 工具可脱离 Agent 单独运行，并返回真实数据或可定位的原文。
- 查询结果包含必要的指标、期间、单位和数据来源；检索结果包含原文、报告身份和位置。
- 使用 train 案例展示基础工具与优化工具的差别，并核对相关原文或数据库记录。
- 原始数据不改，索引可重建，不把参考答案混入索引。
- 提交独立的数据优化配置、构建命令、验证记录和已知局限。

B 的 PR 由其他成员按实际安排审核，不设置固定审核人。交给 C 的材料包括处理流程要点、参数、预处理耗时、结果文件路径，以及至少一个成功或失败案例的证据位置。

## 5 C 的工作与验收标准

### 5.1 开发范围

C 从同一个基线版本创建分支，重点改善 Agent 的行动和结果检查：

1. 在基础提示词和工具之上，设计一个可复用的财务分析 Skill。Skill 指按条件调用的任务指导，不是按题号保存的答案或固定 SQL。
2. 组织公司与指标定位、期间确认、单位检查、重复披露核对、计算条件检查和回答依据检查。
3. 改善查询无结果、检索不相关、工具报错和证据不足时的恢复策略，以及继续查询和结束任务的条件。
4. 根据 train 的答案、日志和反馈积累可复用规则。若采用 memory，初始内容必须版本化，并能在每题开始时恢复。
5. 保留基础策略，提供独立的策略优化开关。使用 A 的基础工具即可运行，不新增对 B 优化结果的硬依赖。

### 5.2 验收与材料

- 在相同工具配置下，可以分别运行基础策略与优化策略。
- 日志能够展示策略引导的真实工具使用，不能只在最终回答中声称执行过检查。
- 规则具有跨公司和跨问题的复用性，无 test 题号、test 答案或评分反馈形成的专用内容。
- train 案例分析说明错误是否减少，以及额外调用和耗时的变化。
- 提交提示词、Skill、可选初始 memory、配置、验证记录和已知局限。

C 的策略 PR 和报告 PR 可以分开提交，由其他成员按实际安排审核，不设置固定审核人。报告写作可以在策略开发期间开始，实验数值以最终保存的结果文件为准。

### 5.3 唯一报告撰写人的工作

C 统一完成问题与数据说明、系统设计、数据工具优化、策略优化、实验设置、结果对比、失败分析、成本与局限、复现说明，以及课程要求的分工材料。

A 提供基线和集成配置、正式实验结果与运行信息；B 提供数据和工具材料。C 根据这些材料编排正文、表格和图，A、B 以 PR 评论或材料勘误反馈事实问题，由 C 修改正文。

报告应说明自动支持率与完整正确率的区别，结合真实案例分析结果；没有提升的优化也如实记录。最终源文件与导出的 PDF 由 C 保持一致。

## 6 接口与目录约定

### 6.1 工具接口

具体函数名和参数由 A 在基础 PR 中确定并写入接口说明。最少覆盖以下能力：

| 能力 | 主要输入 | 返回信息 |
| --- | --- | --- |
| 数据结构与指标发现 | 公司标识、表名或指标关键词 | 表结构、候选指标、相关元数据 |

## 7 PR 提交与审核规则

### 7.1 审核安排

| PR 作者 | 审核安排 | 适用范围 |
| --- | --- | --- |
| A | 由 B 或 C 按实际安排审核，不固定账号 | 基础 demo、公共框架、集成、统一评测、运行说明和后续修复 |
| B | 由 A 或 C 按实际安排审核，不固定账号 | 数据准备、指标发现、检索和工具优化及后续修复 |
| C | 由 A 或 B 按实际安排审核，不固定账号 | 提示词、Skill、策略、报告源文件、PDF 和后续修复 |

**不设置固定审核人，也不在创建 PR 时自动请求固定账号。** 每个 PR 由至少一名作者以外的成员按小组实际安排审核。作者根据评论修复后，由参与审核的成员复查；获得批准且阻塞问题解决后才能合并。作者不自行批准自己的 PR。

上述原则适用于后续 PR。A 进行代码集成或解决冲突时，若产生新的代码修改，应通过自己的 PR 交其他成员审核。报告由 C 修改，其他成员通过评论反馈审阅意见。

### 7.2 分支与开发顺序

1. A 在 `codex/financeqa-demo` 完成基础 PR，目标为 `main`，经其他成员审核后合并。
2. 记录合并后的基线提交号。B、C 分别从该版本创建 `codex/financeqa-data-tools` 和 `codex/financeqa-agent-skill`。
3. B、C 保持各自改动范围，提交可独立运行的优化 PR，由其他成员审核；两者没有强制先后顺序。
4. A 按已批准的 PR 完成集成，在独立分支补充组合配置和公共修复，交其他成员审核。
5. C 的报告可使用 `codex/financeqa-report` 单独提交，交其他成员审核。报告中的最终数值对应集成后的实验记录。

开发期间，A 不覆盖 B、C 正在负责的文件。新增公共依赖或必须修改公共框架时，PR 中明确列出影响范围；需要先行公共修复的，由 A 提交并交其他成员审核，B、C 同步该提交后继续。

### 7.3 每个 PR 必须说明的内容

- 本次解决的问题及范围。
- 改动文件与是否影响接口、依赖、配置或准备产物。
- 可复制的运行和验证命令，及实际执行结果。
- 使用的 train 题目范围、配置、提交号与结果位置。
- 与基线的比较，或本次不涉及效果比较的原因。
- 已知局限和需要重点审核的内容。

审核以真实运行结果、代码和保存的实验记录为依据。报告 PR 需核对指标来源、图表、配置、首次正式 test 结果及 PDF 内容；计划中的结果不能写成已完成结果。

## 8 阶段交付安排

| 阶段 | A 的工作 | B 的工作 | C 的工作 | 阶段完成条件 |
| --- | --- | --- | --- | --- |
| 基础搭建 | 已完成功能开发与 demo 自验，提交基础 PR | 阅读规则，按安排参与审核 | 阅读规则，准备提纲，按安排参与审核 | 其他成员批准，A 的基础 PR 合并，基线提交号确定 |
| 并行优化 | 完整 train 基线、统一评测与公共运行维护 | 独立实现并验证数据工具优化 | 独立实现并验证策略优化，开始写报告 | B、C 各自提交包含验证材料的 PR |
| 审核集成 | 核对接口、集成并提交 PR，按安排参与审核 | 修复审核问题，按安排参与其他 PR 审核 | 修复审核问题，整理案例，按安排参与其他 PR 审核 | 各 PR 经其他成员批准，集成版可运行 |
| 对比与冻结 | 跑 train 对比，记录最终配置和版本 | 核对数据与检索相关结果 | 分析策略表现，填写报告实验部分 | 根据 train 确定最终方案并冻结 |

| 最终提交 | 复现、核对报告事实、整理运行说明 | 复查工具和数据准备说明 | 完成报告、PDF 和报告 PR | PR 审核完成，代码与提交材料对应一致 |

各阶段以交付条件推进，不在人员、模型服务和预算尚未确定时指定固定工期。

## 9 实验与正式测试安排

### 9.1 train 对比

由 A 统一组织以下四种配置，B、C 配合解释各自优化的表现：

| 配置 | 数据工具 | Agent 策略 | 作用 |
| --- | --- | --- | --- |
| 基础版 | 基础实现 | 基础策略 | 建立基线 |
| 数据优化版 | B 的优化实现 | 基础策略 | 检验数据工具优化 |
| 策略优化版 | 基础实现 | C 的优化策略 | 检验策略优化 |
| 组合版 | B 的优化实现 | C 的优化策略 | 检验组合效果 |

比较时保持模型、数据、题目、工具预算、停止条件和检查器配置一致。B、C 可以在 train 子集上开发，最终正式对比覆盖全部 37 道 train 题。每次实验使用独立目录，保存代码版本、配置、准备产物版本、预测和日志。

记录总体和分公司的支持率、矛盾率、信息不足率、服务失败情况，以及耗时、工具调用次数和可获得的模型用量。预处理成本与逐题成本分开记录。数值、期间、单位和证据质量结合案例人工核对，不能仅依赖自动支持率。

### 9.2 正式 test

1. 根据 train 结果选定最终配置；组合版是否采用也在此时确定，不根据 test 分数选择方案。
2. 固定代码、工具、提示词、Skill、初始 memory、索引和其他准备产物，保存提交号和配置快照。
3. A 使用固定系统自动完成全部 19 道 test 题，每题从相同初始状态开始，上一题产生的状态不带入下一题。
4. 先保存整批预测、日志与运行配置，再运行独立评测。作答 Agent 不读取 `evaluation_only/`、评分输出或导出的评测请求。
5. 保留首次正式结果，不利用 test 参考答案或评分反馈修改方法。反馈后的额外探索另行标注，不能替换首次结果。
6. 如检查器服务失败，只对已保存的同一批预测修复评测服务并重评，保留失败记录；不借此修改回答。

官方检查器使用模型对已保存的回答作支持性判断。支持率为 `CORRECT_INFO` 题数除以全部评测题数，可包含部分或间接支持，不等于严格完整答对率。缺失和空白回答计为信息不足；服务或解析失败仍在分母中，须检查 `evaluation_complete` 后再比较效果。原评测程序和提示词保持不变。

## 10 材料交接与完成检查

### 10.1 A 向 B 和 C 交付的基础材料

- 已合并的基础 PR 和基线提交号。
- 安装与运行命令、工具接口说明、配置示例和数据路径约定。
- demo 使用的 train 题目、预测、真实工具日志和验证结果。
- 基础配置与优化配置的切换方式、日志结构、每题状态重置方式。

### 10.2 A 和 B 向 C 提供的报告材料

| 提供人 | 材料 |
| --- | --- |
| A | 架构与决策流程要点，模型和依赖版本，四组 train 实验结果，最终 test 配置及结果，耗时与用量，复现命令 |
| B | 数据处理与检索方法要点，索引参数和构建命令，预处理成本，查询和检索案例，来源位置与已知局限 |

每份材料注明对应提交号、配置和结果文件路径。C 负责将材料写入报告并制作图表，A、B 核对事实。任何人的口头估计都不能替代实验记录。

### 10.3 最终完成条件

- A 的 demo 已由其他成员审核并合并，B、C 从共同基线开展开发。
- 各成员的优化、集成及后续 PR 由作者以外的成员审核，不设置固定审核人。
- 系统使用真实工具并自主处理不同公司和问题，预测符合老师协议。
- 四组 train 对比及正式 test 的配置、结果、日志、成本和版本可追溯。
- 原始数据、协议、评测程序和评测提示词保持不变，test 使用符合规定。
- C 独自完成报告撰写、整合和 PDF 导出，A、B 的材料和事实反馈已处理。
- 运行说明能复现数据准备、作答与评测；模型密钥不进入版本库或输出。
- 最终代码版本、报告数值、图表和提交材料相互对应，分工比例按实际贡献填写。
